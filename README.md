# RUDA WeChat Mini Program

Open the repository root in WeChat Developer Tools. The root `project.config.json` points to this native mini program directory and contains the registered AppID.

The API client and product images use `https://ruda.fashion`. URL checking is disabled in the local Developer Tools project settings so the simulator can load images before the AppID's download-domain allowlist is configured. Before release, enable `https://ruda.fashion` as both a WeChat request domain and a download domain in the WeChat Mini Program admin console, then turn URL checking back on and verify on a real device. Any other image host must also be added as a download domain.

The visible bottom tabs are Home, Merchants, ModaUI, Fashion, and Profile (我的); Home is the launch page and is the marketplace. The Profile tab is the account center: it shows the real buyer or merchant identity with verification state, a server-driven order status summary (待付款 / 待发货 / 运输中 / 售后服务), vault authorizations, notifications, settings, and an authorization-code store finder that stays hidden behind a button. The Fashion section is an immersive vertical full-screen feed backed by the shared `/api/fashion/*` endpoints (`posts`, `editorial`, `merchants`, `social`, `posts/mixed` upload); it renders real server data only and never falls back to demo posts. The Fashion tab and page are controlled by the platform switch `fashion_enabled` (see `docs/engineering/modules/platform-feature-flags.md`); when the platform closes the module the tab is hidden, the page redirects home with an explicit closed notice, and the server rejects `/api/fashion/*` with 403. Store lookup accepts only the 6-digit merchant store code, validated by `GET /api/merchants/code/:code`; the code merely resolves a public storefront and never grants vault access, so protected products still require a server-approved vault authorization. The profile page's 授权码找店 dialog sends the same 6-digit code and enters the real store page; the legacy `RUDA-…` credential branch in `pages/find-store` has no server implementation (`POST /api/vault/store-access/redeem` does not exist) and is not offered from the profile page. Settings remain a separate page opened from the Profile tab and the Home header menu. Settings include account preferences, privacy/terms, account login, and app information. Language, currency, and monochrome preferences sync to eligible RUDA accounts; the mini-program UI itself currently supports Simplified Chinese, and its currency selection is a display-only estimate (orders remain EUR). The mini-program does not load RUDA Web marketing analytics. Marketplace product details support SKU selection and a local cart. Checkout submits bank-transfer orders to the existing buyer API; order history and cancellation use the existing buyer order endpoints. The merchant workspace supports tenant-authorized product creation (one initial SKU), editing core product fields, publish/draft status changes, order listing and fulfillment transitions, and inventory balance adjustments. Merchant and employee accounts continue to use their existing account login. Admin login is intentionally not included.

Buyer favorites, followed merchants, browsing history, and an address book are not implemented on the buyer side, so the Profile tab does not show entries for them; checkout collects the shipping address for each order. Vault authorizations are read through `GET /api/vault/authorizations` (buyer token scoped) and applications still go through the existing `/api/vault/request` flow. Deploy the server before shipping a mini-program build that reads the authorization list, otherwise that block shows a load error instead of data.


Login and account creation share one page with a simple switch. New buyer accounts use email verification and a password; the form links the user service agreement and privacy policy. Merchant and employee login keeps using the same page without a role selector. Merchant registration entry points open the unified web application at `https://modaui.com/register-wholesale?registration=merchant`; mini-program buyer registration does not grant merchant permissions.

Buyer accounts support WeChat login only after an explicit, authenticated account binding. The server exchanges the one-time `wx.login` code using `WECHAT_MINIPROGRAM_APP_ID` and `WECHAT_MINIPROGRAM_APP_SECRET`. The server AppID must match the registered AppID in `project.config.json`. Keep the AppSecret in the server secret manager; never put it in this directory or client-side configuration. Rotate any AppSecret shared outside the secret manager before configuring these variables.

An unbound WeChat identity is never attached automatically to an existing RUDA account. The buyer must first sign in with the existing RUDA buyer credentials and explicitly confirm binding. Identity records are scoped by mini program AppID and link only to buyer accounts. Deploy the migration in `prisma/migrations/20261017090000_add_miniprogram_identity/` before using WeChat login or binding.

The checkout flow does not charge a payment method. Online WeChat Pay, adding additional SKUs through the mini program, and certain advanced merchant settings are not implemented. The payment provider, object storage, database migration deployment, WeChat request/download/upload domains, approved server secrets, eligible test accounts, staging API, and real-device review remain release prerequisites. Test with WeChat Developer Tools against staging before submission.
